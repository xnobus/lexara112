# Wrong letter spacing - two fonts sharing one glyph cache

## Symptom

Reported by Jhinzuo (Chinese Turtle WoW repack, Win11, latest DXVK, pfUI + pfQuest):
with `lexara112.dll` loaded, text everywhere had "wrong spacing" - the quest tracker,
chat, nameplates, pfUI's panels - and changing the load order in `dlls.txt` did not
help. Switching pfUI to the default font, or turning pfUI off, did not help either.

What the screenshots show once the same line is put side by side with and without
the DLL:

- **The line is exactly as long in both.** "Bright Dream Shard: 5/5" is 186 px with
  Lexara and 187 px without it. The client's advances are untouched.
- **The glyphs are not.** In ContinuumCN text they come out ~15-20% narrower than the
  client's own, so each one sits at the left of a cell too wide for it: `5 /5`,
  `0 /1`, `[6 0]`, `3 . 0 . 0 +`. In text set in the client's default font the
  opposite happens - glyphs too wide for their cells, `Keyto` with the space eaten.
- **Some are a different design.** The `1` drawn by Lexara has a flag at the top.
  ContinuumCN's `1` is a plain bar - 1.43 px of ink centred in an 8.8 px advance at
  14 ppem, which is exactly what the screenshot without the DLL shows.

A glyph of another typeface cannot come from the typeface's own outlines, so the
question was where a different font's glyph could enter.

The log showed nothing wrong (device caught, shaders bound, no rejected uploads) apart
from the known atlas pressure of this repack - three 8-9 MiB CJK faces, sixteen face
registrations, evictions.

## Cause

The on-disk glyph cache (`%TEMP%\LEXARA\<family>_<style>_s96_sp12`) was named from
`FT_Face::family_name` and `style_name` alone. Those are not an identity of the file:

- FreeType fills them from the **WWS / typographic names (IDs 21, 16, 17) before the
  legacy IDs 1 and 2** (`sfobjs.c`, `sfnt_load_face`).
- Font repacks typically rename only IDs 1, 4 and 6. The `ContinuumCN.ttf` from the
  report says `continuumCN` in 1/4/6 and still carries **`War Sans CN` /
  `UI Condensed Medium`** in 16/17 - the names of the base font it was merged into.

The report's log shows two more 8-9 MiB CJK faces (8438732 and 8024976 bytes) next to
ContinuumCN (9338332). Those files were not available, so that one of them reports the
same pair is inferred, not read: the glyphs Lexara drew in ContinuumCN text are a
different, narrower design, and the name pair is the only way the code lets another
file's glyphs in. Every typeface with that pair resolved to
`War Sans CN_UI Condensed Medium_s96_sp12`. Each
`MSDFCache` loads the manifest and merges its writes into the shared block files, so a
codepoint generated by one font was served to the other from then on - its shape,
`bitmapLeft`, `bitmapTop` and cell size, placed by `ProcessGeometry` at the pen
position and advance the client computed from the *real* font. Which font "wins" a
codepoint depends on which one asked for it first, and the result persists across
sessions, which is why nothing the reporter changed in game made a difference.

It never showed on the development machine: every folder in its `%TEMP%\LEXARA` has a
distinct name pair.

## The change

- `MSDFCache::GetCacheBasePath` puts the font file's hash in the folder name:
  `<family>_<style>_<16 hex digits>_s96_sp12`. The hash is the `HashFont` value the
  constructor already computed for `MSDFManager::RegisterFont`, so there is no extra
  cost per face. It samples the length plus head, middle and tail windows; the head
  holds the table directory with every table's checksum (`glyf` and `hmtx` included),
  so two files that differ in any outline or advance get different folders, while the
  same file opened for several sizes still shares one.
- `MSDFPregen`'s cache probe passes the font data, so it looks at the same folder the
  game uses.
- `font registered` log lines now carry `family` and `style`, so a future report shows
  directly whether two files report the same pair.

Every existing cache folder is left behind under its old name and never read again:
glyphs are regenerated once on the first start, and the polluted caches cannot leak
back in. The old folders can be deleted by hand (`%TEMP%\LEXARA`); the DLL does not
delete them, because an older build running at the same time may still have them
mapped.

## What this does NOT change

- Atlas capacity. The repack still registers many faces and the log still shows
  `atlas eviction` lines - see `docs/atlas-upload-stutter.md` for that lever.
- Glyph placement for a font whose cache was never shared - that path is untouched.

## Verification

Built 2026-09-13, no new warnings. Two runs on the test client, login screen only:

- **Run 1 (cold):** `font registered ... family='Friz Quadrata TT' style='Regular'`
  (likewise Arial Narrow, Skurri); three new folders, e.g.
  `Friz Quadrata TT_Regular_66B7FA826BFBEB71_s96_sp12`; glyphs generated, text sharp
  and spaced as before; on exit the manifest and `block_0.dat` were written.
- **Run 2 (warm):** no new folders (the hash is stable across processes), and
  `upload: no pixels (code=32 ...)` - the space coming back through `TryLoadGlyph` -
  shows the glyphs were read from the hashed folder. The rendering matches run 1.

Not reproduced end to end: that needs two font files with the same name pair loaded
by the client. **To be confirmed on the reporter's client** - his quest tracker should
show `5/5` and `0/1` without gaps and a `1` without a flag, and his log should show
`ContinuumCN` and his default font both reporting `family='War Sans CN'`.
